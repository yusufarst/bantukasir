Every HTTP route of BantuKasir V1: its method and path, the handler that serves it, the permission it checks and the result it returns. Pages are those of INFORMATION_ARCHITECTURE section 5; controls are those of INTERACTION_INVENTORY, whose "RF-5" route column is answered control by control in INTERACTION_CONTRACTS section 9. Validation and error results per command are INTERACTION_CONTRACTS sections 2 to 7. This document adds no business rule; it applies TECHNICAL_RULES and SECURITY_MODEL. Pages are named by their INFORMATION_ARCHITECTURE identifier and working label; the titles users see are those of COPY_DECK section 4.1 (COPY_DECK finding F-03). Route identifiers are permanent: `RP-` pages (numbered as their page, `RP-101` serves UXP-101), `RD-` JSON reads, `RA-` authentication and sign-in session endpoints, `RR-` requests that are not commands, `RC-` commands, `RN-` navigation redirects, `SC-` scheduled commands and `OP-` operator procedures.

## 1. Conventions

| ID | Rule | Source |
| --- | --- | --- |
| RT-01 | **One same-origin application.** Laravel routes render Inertia pages; JSON is used only by the reads of section 3, the commands of section 6 and the requests of section 5. There is no public API, no token API and no `DELETE` route. | TR-HTTP-01, TR-HTTP-04 |
| RT-02 | **Paths and names.** Paths are English, lower case and kebab-case, and name the resource the page shows; record identifiers in paths are internal keys, never document numbers. Route names are dotted (`sales.show`). Command paths are `/commands/<operation>` with the operation of section 6, which is also the envelope's `operation` (ADR-007 section 1). Paths and names are technical identifiers, not copy (PROJECT_RULES section 11). | AGENTS rule 14, ADR-007 |
| RT-03 | **Handlers.** A page route calls one controller method that runs one Query and returns one Inertia page built from a DTO. A command route calls an invokable controller that resolves one FormRequest (validation allowlist, capability and object scope) and one Action (the transaction). Controllers hold no business rule. Handler names follow STACK_AND_MODULES section 3: `Http/Controllers/<Module>/…`, `Http/Requests/<Module>/…`, `Actions/<Module>/…`, `Queries/<Module>/…`. | TR-HTTP-03, ARC-01 to ARC-02 |
| RT-04 | **Middleware stack** of every authenticated route, in order: HTTPS and trusted host; session; authentication; active account (SEC-AUTH-09); sign-in session limits (30 minutes idle counted from user-initiated requests, 12 hours absolute; SEC-SESS-02); CSRF on every non-`GET` route (SEC-HDR-01); rate limit (RT-09); capability gate (RT-05); recent authentication where section 6 says so (SEC-SESS-05). Pre-authentication routes (RP-001, RP-002, RA-01, RA-06) skip authentication and add guest-only and their own throttles. The health route RH-01 runs no session middleware at all, only HTTPS, trusted host and its throttle. | SECURITY_MODEL sections 4, 5, 11, 12 |
| RT-05 | **Permission.** Each route names the capability that opens it (the "gate"); a route with no gate does not exist, and a route-inventory test proves it (SEC-AZ-01). The gate is checked by middleware before the controller; object scope (SEC-AZ-03) is checked by the FormRequest or the Query; the in-transaction guard re-checks the actor (SEC-AZ-04). An object that does not exist and an object outside the actor's scope give the same `NOT_FOUND` answer (TR-ERR-03). A page shows only the sections and controls the actor's capabilities allow; hiding is never the authorization (SEC-AZ-07). | SECURITY_MODEL section 5 |
| RT-06 | **Responses.** Pages: Inertia `200`, or a `302` named in the table. JSON reads: `200` with the DTO of the role. Commands: `201` when the command committed now, `200` when the original result of a repeated identity is returned (ADR-007 section 3), and the error answers of TECHNICAL_RULES section 4. Every authenticated response is `Cache-Control: no-store, private`, except media (RD-07, `private`), and carries the security headers of SEC-HDR-02 and the content security policy of SEC-HDR-03. | TR-HTTP-05, TR-HTTP-09, SEC-CH-06 |
| RT-07 | **Error body.** A refused JSON request returns `{ "outcome", "code", "messageKey", "params", "fields", "lines" }`: `outcome` is `REJECTED` or `HELD`; `code` is one of the 32 codes of TECHNICAL_RULES section 4 (UI_STATES section 3); `messageKey` is the COPY_DECK key of section 13.1; `params`, `fields` (field path → message keys) and `lines` (line index → safe values such as available stock) carry only safe values (TR-ERR-02). No new error code is introduced by RF-5. | TR §4, COPY_DECK section 13 |
| RT-08 | **Paging and filters.** List pages and reads accept only the query parameters their row lists; anything else is refused `VALIDATION_FAILED` (TR-VAL-07). Keyset lists use `after` (an opaque cursor of the last row's sort key) and `before`; Product Search uses `page` (TR-PAGE-01, TR-PAGE-02). Page size is 25 by default, at most 100 (`perPage`). A cursor never grants access (TR-PAGE-03). Nothing sensitive is put in a query string (SEC-CH-06). | TR sections 11.4 and 12 |
| RT-09 | **Rate buckets** (SECURITY_MODEL section 11): `signin` (RA-01), `link` (RA-06), `confirm` (RA-03), `search` (RD-01, RD-05, RD-06: 300 per minute per user), `command` (every RC route: 60 per minute per user), `photo` (RC-25: 200 per hour), `logo` (RC-32 with a logo: 20 per hour), `csv` (RR-01: 30 per hour), `print` (RC-44 to RC-47: 60 per minute), `link_issue` (RC-35, RC-41: one new link per account per 60 seconds), and `authenticated` (every route: 600 per minute per user). A throttled request answers `THROTTLED` with `Retry-After`. | SECURITY_MODEL section 11 |
| RT-10 | **Background requests.** RD-03 and the automatic repeats of RC-50 carry the header `X-Background-Request: 1`; the sign-in session middleware does not count them as user activity (SEC-SESS-02, TR-HTTP-10). The header can only make a request not count. | SEC-SESS-02 |
| RT-11 | **Request receipts.** Every `RC` request that carries a command envelope — every one but the status check RC-50 — is recorded on arrival, in a short transaction of its own before the command runs, as a command request receipt holding the actor, operation, intent, key, epoch and received time, never the payload; its outcome is marked after the command ends, or settled by a conclusive status check or a restore reconciliation of its intent (ADR-009 section 1). The receipt is what RD-04 lists. | ADR-009, D-074, D-089 |
| RT-12 | **Request body limits.** JSON and form bodies at most 1 MiB; RC-25 at most 8 MiB, RC-32 at most 5 MiB, RR-01 at most 2 MiB (SECURITY_MODEL section 13), each enforced at the proxy, PHP and in validation. | TR §11.4, SEC-UP-02 |

## 6. Command routes

Every route is `POST /commands/<operation>` with a JSON body (multipart for RC-25 and RC-32) carrying the envelope of ADR-007 section 1, contract version 1. The handler is `Http/Controllers/<Module>/<Operation>Controller` (invokable) → `Http/Requests/<Module>/<Operation>Request` → `Actions/<Module>/<Operation>`; the Action takes the locks of the TECHNICAL_RULES section 7.2 family named. Every command may also answer the common refusals `UNAUTHENTICATED`, `CSRF_FAILED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_FAILED`, `IDEMPOTENCY_CONFLICT`, `EPOCH_STALE`, `INTENT_ABANDONED`, `THROTTLED` and `SERVICE_BUSY`, and `RECENT_AUTH_REQUIRED` where recent authentication applies. The payload, validation and result of each are INTERACTION_CONTRACTS section 5.
