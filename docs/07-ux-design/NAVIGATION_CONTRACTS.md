Where every page comes from, where its back and cancel lead, where success and errors take the user, and what is kept on the way. Pages are those of [INFORMATION_ARCHITECTURE](INFORMATION_ARCHITECTURE.md) section 5; states are those of [UI_STATES](UI_STATES.md). Global rules are numbered `NC-nn`; identifiers are permanent. This document adds no business rule.

Indonesian labels in quotation marks are **working labels**, taken from the [GLOSSARY](../02-domain/GLOSSARY.md) where it has a term; they stay provisional until gate P7-G2 (terminology and copy, RF-4B). Nothing here is visual design (RF-4C, gate P7-G3) or an HTTP route (RF-5).

## 1. Global rules

| ID | Rule |
| --- | --- |
| NC-01 | **Contextual, deterministic back.** Every page that is not reached from the navigation has a visible back action naming its destination ("Kembali ke …"); where the destination depends on how the page was opened, the label names the page actually returned to. Back never depends on browser history alone. The destination is the one in the page's contract (BACK ACTION); where the contract leads back to the page that opened it, that is the page the user came from when that page is one of the entries listed in the contract, otherwise the parent (AICWDF section 18.4). When a page is reached through an entry "the success of …" (NC-08), the command page that led there does not count as the page the user came from: the back action leads to the parent, never back to the completed form (NC-04). On a create, edit or command page the back action uses the same unsaved-changes guard as cancel (NC-03). |
| NC-02 | **Top-level and sub-navigation pages have no back action;** the navigation stays visible and is the way out. |
| NC-03 | **Cancel** exists on every create, edit and command page. It sends nothing, with one exception: "Batalkan impor" on UXP-308 sends the request that removes the import's temporary file (D-054; TR-CMD-03). When data was entered, the unsaved-changes guard (UXS-45) asks first, with "Tetap di halaman ini" as the default. |
| NC-04 | **Browser Back** is allowed everywhere and never resubmits a command. After a command is COMMITTED, Back from its result page goes to the contract's back destination, not to the filled form. A one-time link is never shown again (SEC-ACC-05). |
| NC-05 | **Direct links and bookmarks** are authorized again on every load (SEC-AZ-06): a page outside the actor's scope, or an object that does not exist, shows UXS-08 with the same answer (TR-ERR-03); a page whose capability the role lacks shows UXS-07. |
| NC-06 | **End of the sign-in session** (idle, absolute limit, revocation) leads to UXP-001 after a full page load; no earlier page can be shown again (SEC-CH-04). A cash session is never closed by it (BR-CASH-11). Unresolved command references survive and are offered after the next sign-in (SEC-CH-05). |
| NC-07 | **Dialogs only for review and confirmation** (UXA-05). Detail, create and edit are pages. Scan capture pauses while a dialog is open (BR-CAT-32). |
| NC-08 | **Success** always lands on a page that shows the saved result; a Sale lands on its receipt with no further confirmation (BR-SALE-14). |
| NC-09 | **Errors** keep the user's input on the page with the reason at the field or line concerned; nothing is cleared except passwords (SEC-CH-03). A definite rejection never changes a payable total silently (TR-ERR-05). An uncertain outcome freezes the request on its page (UXS-14) and never sends the user to start again. |
| NC-10 | **State preservation.** Lists keep their search, filters, sort and page when the user returns from a child page, within the sign-in session, in the encrypted history state (SEC-CH-04). Drafts that hold cost (receiving, adjustment, opening stock, cost correction on UXP-504) live in page memory only, never in browser storage (BR-INV-17, SEC-CH-05). |
| NC-11 | **Pages over a working page.** UXP-303 opened from UXP-405 or UXP-413 covers the working page without leaving it; its back and cancel return to the working page with the draft untouched; its success adds the new product to the draft (UXA-05). |
| NC-12 | **Home per role** after sign-in and from "Kembali ke halaman awal": Owner UXP-007; Ops UXP-401; Cashier UXP-101, or UXP-104 without an OPEN session; Combined UXP-101 with an OPEN session, otherwise UXP-401. |
| NC-13 | **No replacement while an outcome is uncertain** (BR-CMD-03, BR-SALE-20, BR-RFD-17, TR-ERR-06). While this user holds an unresolved reference (UXS-14, UXS-15) of a command family of TECHNICAL_RULES section 7.2, the client starts no new command of that family. Repeating the same request ("Kirim ulang") and resolving it ("Cek status", UXP-006) are not new commands and stay available; print, reprint and export requests are exempt, because they never repeat or change a business fact (BR-SALE-21). (a) Every control that would start a new command of that family is disabled with the reason (UXS-13), which carries the link to UXP-006; the rows of INTERACTION_INVENTORY state it for the entries of the critical families (ADR-007 section 1): "Bayar" for Sale checkout, the close entries, and the entries of refund and return, receiving, manual issue and adjustment, reversal, opening stock, onboarding, cost correction, CSV import and barcode correction. (b) A command page of that family that is opened anyway — by browser history, a bookmark or a direct link — opens in UXS-14 or UXS-15 with that reference and its uncertain panel, never as a new draft, and offers no new final or confirm action; this covers every family, including opening a cash session (UXP-104) and the master-data, configuration and user-management families, whose page stays on the shared uncertain panel of UXP-000. (c) The family is read from the stored reference (its operation, SEC-CH-05), so the block holds for the whole family, not for one object, and survives a reload, a sign-out and a new sign-in session in the browser that holds the reference. It acts only in that browser: on another device, in another browser or after the browser's site data are cleared, the reference is unknown and nothing blocks a new draft, and the server does not recognize that draft as a replacement, because it carries a new source intent (ADR-007 section 1). This gap is not an accepted risk: RF-5 proposes its backend mitigation and tests, with any Owner revalidation they need (D-074; OPEN_ITEMS N-07). (d) Within the user-management family, deactivating an account and revoking a link stay available while the unresolved reference is any other operation of that family (for example create, role change, name or email change, reactivate, anonymize, issue a link), because they only end access and must remain usable at once: deactivation under D-069 (d), and revocation because it is one of the controls on which the Owner accepted the risk of one-time links (D-056); while the unresolved reference is itself a deactivation or a revocation, that operation is blocked like any other, because the reference does not say which account or link it concerns. (e) The block ends when UXP-006 or the page's own recovery resolves the reference. When a Sale checkout resolves as COMMITTED — through "Cek status" on UXP-102 or on UXP-006 — its cart is discarded and its receipt (UXP-103) is its result page, so the same goods are never offered for payment again from that cart. A reference refused as EPOCH_STALE after a restore keeps its status check ("Cek status" on UXP-006 and on the page's uncertain panel): the server answers it from the restore reconciliation that the Owner carries out under the restore runbook, and until that reconciliation has recorded an outcome the answer is EPOCH_STALE again and the family stays blocked for that user (UXS-15). The reference is released only by a verified outcome: COMMITTED, or a NOT_COMMITTED that an audited reconciliation recorded with a safe fence. The client never clears it and never repeats its request. The reconciliation lets the Owner's own user-management references be resolved before the security changes of SECURITY_MODEL SEC-OP-04 are re-applied, so that NC-13 never prevents that re-application (D-073; the mechanisms are specified in RF-5 and RF-6). NC-13 is a client rule that applies the rules above; it adds no server refusal. RF-5 names the existing mechanisms that back it (source intent and fences, ADR-007) and proposes the mitigation of (c) (D-074); any new server refusal would first need the Owner's decision. |
