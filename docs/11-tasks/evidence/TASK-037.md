## 3. Readings and technical choices

| ID | Reading or choice |
| --- | --- |
| C-1 | **OP-04's audit.** INTERACTION_CONTRACTS section 8 names one action code for OP-04, `ONBOARDING_RESTORE_HOLD`, and SEC-LOG-02 lists no epoch or session revocation among the business audit events; SEC-LOG-03 puts session revocations and operator procedure runs in the security log. So OP-04 writes its business audit event when it sets a hold, and its run and each account whose sessions ended are always in the security log; a restore of RELEASED data writes no audit event, as OP-07 writes none when it changes nothing. No action code is added |
| C-2 | **The hold moves the version, not the state's last change.** SCHEMA section 5.7 moves the version "with every restore hold"; the state does not change, so `changed_at` and `changed_by_user_id` stay as restored and RP-412's "aktif sejak" still reads when the period began (TASK-035 R-10). RELEASED_BEFORE_RESTORE changes the state: the version one on, `changed_by_user_id` null for an operator procedure (SCHEMA section 5.7). NEVER_RELEASED changes nothing of the row |
| C-3 | **Every hold is decided.** OP-04 sets a hold whenever the restored state is not RELEASED (SCHEMA section 5.7, "whenever"), also when the restored data hold an unreconciled hold of an earlier restore; onboarding stays held while any hold lacks its decision. Once one decision released onboarding, a later NEVER_RELEASED is refused — nothing undoes a release (G-26) — and RELEASED_BEFORE_RESTORE records the decision without a second release record |
| C-4 | **The fence's actor and epoch.** `command_identities_kind_shape` requires a FENCE's actor to be a user, so OP-05's fence names the Owner who decided, in the current epoch, with the reconciliation's time as its received time; the receipts settled by it name the same Owner (SCHEMA section 5.3, `settled_by_user_id`). A report whose intent has an identity — committed in the restored data, or fenced — or whose epoch is the current one is refused: the status check answers it. One decision per run, the order of RB-01 steps 16, 18 and 19 being the operator's |
| C-5 | **OP-08's checks.** SEC-OP-08 records "the backup restored, as in backup_runs" and the manifest's SHA-256: OP-08 requires a row of `backup_runs` of this identifier with a stored manifest, and, for a drill that passed — which verified that manifest (RB-02 step 3) — the SHA-256 of the manifest object as its upload recorded it; a failed drill is recorded with what was measured. A drill's end is not in the future and its restore time is within its span. SEC-OP-08 names no audit event and INTERACTION_CONTRACTS section 8 no action code: the row, whose actor is the procedure with the note, and the security log entry are its record |
| C-6 | **The sequence advance is a psql script**, because SCH-46 gives it to the migration role, whose credential the operator holds on the operator's machine at RB-01 step 9, not the application's container (ENVIRONMENTS section 11). Each sequence is set to the greater of its restored value and the highest counter of the gap review, plus 100,000, so that both readings of RB-01 step 13 hold |
| C-7 | **The TS-24 restore over the test database.** The tests may reset only the test database (TS-07), and no role of the application may create one, so a TS-24 restore is RB-01 step 9 over that database: `pg_restore --clean --if-exists --single-transaction` as the migration role, which owns every object, with the extension left out of the list, because the database keeps it from its setup and the migration role may not create it; then `db:apply-grants` and `db:check-privileges`, because the dump holds no privilege |
| C-8 | **The rehearsal in CI.** "Locally" is the local environment of compose.yaml, which runs on CI's runner under D-108; the job `Restore rehearsal` starts it with the services of the profile `rehearsal`. The target's application is the development stage of the same image definition, as the local environment runs it (TASK-012); a real drill deploys the manifest's release image (RB-02 step 2), which the job `Image checks` builds and checks. The store is the local test server; the passwords, the recovery key and the SSH keys are made at run time, masked in the log, and destroyed with the target. The source's synthetic data — Toko Contoh, a logo as a stored file and a closed cash session with a Sale in each method — come from the browser fixtures of the local environment |
| C-10 | **TASK-035's tests keep their rows of holds** (TASK-035 review R-09). `OnboardingCommandsTest` and `OnboardingPagesTest` prove each command's and page's guard of a hold with rows written as the runtime role, at fixed versions and in one sign-in session, which OP-04 would end; the hold of OP-04 and the decisions of OP-05 are proven end to end, through TS-24 restores, by `AfterRestoreTest` and `RestoreReconciliationTest`. The writers of the holds are now named: the Inventory module's `OnboardingState` alone (`OnboardingCommandsTest`, STK-12) |
| C-9 | **The manifest read by the operator's scripts.** The operator's machine needs no JSON tool: `fetch-backup.sh` reads the manifest of format 1 that `BackupRunner` writes, in its fixed order, with fixed patterns, and refuses anything else; `compare-counts.sql` reads it with PostgreSQL's own JSON functions in a read-only transaction |
