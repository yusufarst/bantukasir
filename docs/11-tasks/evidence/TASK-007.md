## 5. Readings and technical choices

- **R-01 The cells of the matrix.** A cell is read by its words (section 4). A restricted cell opens no gate by itself: CAP-02 of a cashier is the till's search, whose route (RD-01, TASK-015) names it with the context; CAP-12 of Operations is the field scope of the receiving pages (TASK-022); CAP-14 of a cashier is the stock that checkout reads (TASK-028), never the stock pages, which ROUTE_CONTRACTS gives to "Owner, Ops, Combined". The capability flags of the shared props are the capabilities that open a gate.
- **R-02 "Signed in" is CAP-01.** ROUTE_CONTRACTS names the gate "Signed in" for RN-01, RA-02, RA-03, RA-04 and RA-07, and CAP-01 ("sign in and out; view own account; change own password") for RP-003, RP-004 and RA-05. Every role holds CAP-01, so these routes are gated `capability:CAP-01`, and no signed-in route is without a gate (SEC-AZ-01).
- **R-03 The gate's place in RT-04.** The framework sorts route middleware by a priority list; `bootstrap/app.php` gives the list of RT-04 — the session, authentication, the sign-in session's checks, CSRF, the rate limits, the capability gate, recent authentication, and only then the route's bindings — so that no object is read for a refused request. CSRF stays in the web group, and the sorted order is proven for every signed-in route (`RouteInventory::violations`).
- **R-04 The object scope and the security log.** A scoped lookup never reads the object before the scope applies, so it cannot tell a missing object from one outside the scope, and neither is a security log entry; a refused gate, a refused policy and a refused actor guard are (`AUTHORIZATION_REFUSED`). Guessing is bounded by the bucket `authenticated`. No route of V1 reads an object by its identifier yet: the pattern is proven on a test-only route (`ObjectScopeTest`).
- **R-05 The actor guard's refusal** is FORBIDDEN for a deactivated account and for one that lost the capability alike (TECHNICAL_RULES section 4: "Capability missing for the role"); the deactivated account's next request is UNAUTHENTICATED anyway, its sessions being revoked (SEC-ACC-08). TASK-008's Action base calls the guard in every command, and TASK-011's deactivation and role change take the update lock that waits for it (TR-LOCK-02).
- **R-06 The shared props.** `auth` holds the user — identity, display name, roles, capability flags — and the sign-in session: the idle limit, the seconds left until it, the instant of the absolute end and the seconds left until it, counted when the answer was made. SEC-CH-02 names "the idle limit and the sign-in session's absolute end time"; the seconds left are those limits as of the answer, so that the browser's clock, which may be wrong, never decides when a session ends, and the instant is what the notice of the 12-hour limit shows (UXA-21). `auth` is shared with every answer, partial reloads included (`Inertia::always`), and is null before sign-in. The recovery epoch joins it with the Task that creates it (TASK-008, TASK-010); the flash message codes stay the pages' own props, as TASK-006 made them; `errors` is Inertia's validation-error channel (SEC-CH-03).
- **R-07 The document title.** COPY_DECK section 4.2 gives the protected pages ":halaman — :toko", the shop's name from the BusinessProfile, which TASK-010 creates (contract section 4.3). Until then the shell titles a protected page with its label alone (`ux.shell.document_title_public`), never with the codename (CW-14); TASK-010 switches it to `ux.shell.document_title`. UXP-003 and UXP-004 are now titled by the shell (TASK-006 reading R-09).
- **R-08 The navigation that exists.** No destination of the navigation exists yet (EXC-52), so a signed-in page shows the account menu and no navigation landmark, and at compact width no menu button (UXI-022 is "compact width only" and would open an empty drawer). Each page Task registers its destination in `resources/js/lib/navigation.ts` with its route and the capabilities of its row of INTERACTION_INVENTORY, in the order of INFORMATION_ARCHITECTURE section 4 that the module holds. The rail, the drawer, the sub-navigation and the badges are proven on the shell's specimen with every destination of every role (`/testing/shell-specimen`, local and testing only, like the component specimen).
- **R-09 The account menu's button** shows the user icon in the avatar's circle, and the display name beside it in the side navigation, rather than the previews' initials: a button whose accessible name is "Menu akun :nama" may show no text that its name does not contain (WCAG 2.5.3; axe `label-content-name-mismatch`, which the first browser run reported).
- **R-10 The client timers.** The browser counts each limit from the moment an answer arrived, by the seconds left that the answer carries, so its deadlines are never earlier than the server's (`resources/js/lib/sessionTimes.ts`). The dialog of UXS-23 opens two minutes before the idle limit (UXA-21: at least 60 seconds), never against the 12-hour limit, which "Tetap masuk" cannot extend; the notice of the 12-hour limit shows its end as a time of day from 15 minutes before it. While the user types, at most one user-activity request a minute (SEC-SESS-02). The tabs of one browser share one sign-in session, so they share their deadlines and a sign-out or an end (`BroadcastChannel`, no storage). When a limit is reached, the browser clears the history key and its storage and loads the application's address, which the server answers with the sign-in page and the note of UXS-09 — the server has ended the session by then — or, when another tab kept it alive, with the home. A page restored from the back-forward cache is loaded again; an answer for another user clears the history key and the storage and reloads.
- **R-11 The note of UXS-09** is shown when the browser had a session — a limit, a revocation or the framework's lifetime ended it — and not on a first visit of the application's address, which is the sign-in page's first entry (NAVIGATION_CONTRACTS UXP-001). TASK-006 showed it on every unauthenticated page load.
- **R-12 The answers of a refusal.** A request that changes something, or asks for JSON, gets the body of RT-07; a page loaded or visited with GET gets the generic page of its state; a server error has no code, so its JSON body is empty (TR-ERR-01); a method that a path does not have is NOT_FOUND, like a missing path. A path that no route serves reads no session, so its page is the same for every visitor, without the shell; a NOT_FOUND or FORBIDDEN of a route that exists shows the shell to a signed-in user and encrypts its history.
- **R-13 Recent authentication** (TASK-006 finding F-7) answers 423 on every channel, which opens the dialog of UXS-11 (TASK-009); TECHNICAL_RULES section 4 writes "redirect to confirmation" for a form, and the confirmation is a dialog of the shell, not a page (UXA-05, INFORMATION_ARCHITECTURE section 4). The 423 body stays the framework's until TASK-008 (OPEN_ITEMS T-26).
- **R-14 Trusted hosts and proxies.** The framework's trusted hosts apply in neither `local` nor the tests, and only once something reads the host; the application's middleware refuses an unknown host with 400 and no body before anything runs, in every environment, against exact names (`APP_TRUSTED_HOSTS`, else the host of `APP_URL`); the local environment trusts `localhost` and `bantukasir-app`, the browser tests' alias. Only the configured proxy hops are trusted (`APP_TRUSTED_PROXIES`), never a wildcard, and only X-Forwarded-For, -Proto and -Port are read; `CF-Connecting-IP` is never read, so on the server the hops are the platform's proxy and Cloudflare's ranges (ENVIRONMENTS section 10), which the operator sets at gate TARGET.
- **R-15 HTTPS and HSTS.** Where `APP_URL` is HTTPS, plain HTTP is answered 308 to the same address over HTTPS; no path is left open for certificate validation, because the origin's Cloudflare Origin CA certificate needs none (ADR-011 item 8). `Strict-Transport-Security` is sent over HTTPS only once the operator sets `APP_HSTS`, after verifying HTTPS on the target (SEC-HDR-02); `includeSubDomains` only with `APP_HSTS_SUBDOMAINS`; never preload.
- **R-16 RH-01.** The framework's health route answers a page that names the application, times the request and loads Tailwind and a font from other origins, against "no detail" and SEC-HDR-03; RH-01 is the application's own route on the framework's `DiagnosingHealth` event, outside the web group, with an empty body and 200 or 503. Its throttled answer is the body of RT-07, never a page.
- **R-17 The bucket `link_issue`** counts per account named by the request's business payload, `payload.userId` (RC-41's `userId`, INTERACTION_CONTRACTS section 5; the envelope of ADR-007, whose JSON keys TASK-008 fixes: `Limits::LINK_ACCOUNT_FIELD` changes with them), read as a key like an object's identifier (`ObjectScope::key`), so that one account never has two counters; a request that names no account as a key — RC-35's new account, or a padded or malformed value that the command refuses — is not counted, and the broker's own throttle stays the check in the transaction.
- **R-18 Caching.** Every answer that has not chosen a cache policy of its own is `Cache-Control: no-store, private` (TR-HTTP-09): a refusal of a signed-in request is never stored either; only media will choose private caching (RD-07).
- **R-19 Nginx.** The local web server adds the headers of SEC-HDR-02 and the baseline policy of SEC-HDR-03 without a nonce to the answers it makes itself — static files and its refusals — and none to the application's, which carry their own. The release image is TASK-012's.
- **R-20 The local environment's health check** asks for a path that no route serves, as JSON, and expects Laravel's NOT_FOUND: it needs neither the migrated database, which RH-01's bucket needs, nor the frontend build, which a page needs, and CI starts the environment before both (`compose.yaml`).
- **R-21 Debug output** is on only where `APP_ENV` is `local` and `APP_DEBUG` is true (`config/app.php`), so a misconfigured staging or production never prints detail (TR-ERR-02).
- **R-22 RA-05's bucket** (OPEN_ITEMS T-30 (d)). RA-05 is now in the bucket of every signed-in request, 600 a minute per user, and a wrong current password there is recorded as `PASSWORD_CONFIRMATION_FAILED` (TASK-006); a bucket of its own, such as the five a minute of `confirm`, would change SECURITY_MODEL section 11 and TASK-006's tests of the password rule, so it is left to the change control that T-30 names.
- **R-23 A sign-in that crosses a password change** (OPEN_ITEMS T-31) is left to TASK-011, which the item also names and which meets the same window with role and status changes. Closing it needs a fingerprint of the password hash that the sign-in itself checked, stored in the session by that sign-in, compared on every signed-in request and kept current by the own password change; Laravel's `AuthenticateSession` stores its fingerprint at the session's first request, after the window, so it would not close it as it is.
- **R-24 The browser tests that sign in a person run one at a time.** The browser fixtures give a person of Toko Contoh a new password at the start of each test, which ends that person's sign-in sessions (TASK-006), and Toko Contoh has four people, one per kind of account (KEY_SCREENS section 5). TASK-006's three files each used a person of their own; the shell's and the baseline's tests need every kind of account, so two files at once ended each other's sessions (the second local browser run, section 8.1). `playwright.config.ts` now runs the tests that sign in a person — `tests/Browser/access/`, `security/`, `shell/shell.spec.ts` and `shell/session.spec.ts` — in a project `people` with one worker, beside the project `chromium` of the other tests, which CI's two workers run in parallel with it. The frame on the shell's specimen signs nobody in and is in the project `chromium` (`shell/frame.spec.ts`), one test for each kind of account at each width, so that each stays within the time of a test on the Owner's machine (TASK-006 finding F-5).
